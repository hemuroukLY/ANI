# 登录模块状态校验调整记录

> 分析日期：2026-09-07
> 范围：auth-service 登录链路（租户密码登录 / 平台登录 / OIDC / Refresh 续期）对照租户状态、用户状态、权限三个维度的管理面设计，识别出的差距与调整方案。
> 依据：`repo/services/tasks/modules/plan/tenant/租户管理plan v3.0.md`（平台角色新增 platform-ops / platform-readonly）、`repo/api/openapi/services/v1.yaml`（角色 enum 已含三角色）

## 二、登录链路检查矩阵（实际实现 vs 设计要求）

| 检查点 | 租户密码登录 | 平台登录 | OIDC | Refresh 续期 |
|---|---|---|---|---|
| 租户 `status='active'` | ✓ LookupTenant | N/A | ✓ CreateSession | ✗ 不查 |
| 用户 `status='active'` | ✓ | ✓ | ✗ 反而重置为 active | ✗ 不查 |
| 用户 `is_deleted` | ✗ 不查 | ✗ 不查 | ✗ 不查 | ✗ 不查 |
| 角色时效 | 登录时快照 | 快照 | group 映射 | 沿用登录时快照（最长 7 天） |

## 三、问题记录与解决办法

### 问题 1：Refresh 续期完全不校验状态（最严重）

**位置**：`repo/services/auth-service/internal/service/refresh_tokens.go` `persistentRefreshTokenStore.Validate`

**现象**：Validate 只校验 `revoked_at IS NULL AND expires_at > NOW()`，不查租户状态、用户状态、软删除标记。

**后果**：

- 租户被冻结/禁用后，其用户在最长 7 天（refresh TTL）内仍可持续换取新 access token，冻结失去强制力
- 用户被 `SetStatus('disabled')` 后同样可继续续期 7 天
- 软删除用户同理

**解决办法**：Validate 的 SQL JOIN `users` 和 `tenants`，校验：

- `tenants.status = 'active'`（或按产品决策的冻结策略，见问题 4）
- `users.status = 'active'`
- `COALESCE(users.is_deleted, FALSE) = FALSE`

不满足时拒绝续期，并顺手 `UPDATE refresh_tokens SET revoked_at = NOW()` 使该 token 失效。

### 问题 2：软删除用户仍可密码登录

**位置**：

- `repo/pkg/adapters/postgres/password_login.go` passwordLoginStore.LookupUser（租户版）
- 同文件 platformLoginStore.LookupUser（平台版）
- `repo/services/auth-service/internal/service/oidc_sessions.go` CreateSession 的 upsert

**现象**：三处用户查询都没有 `is_deleted` 过滤，而管理面（用户计数、状态变更）均已过滤软删除。

**解决办法**：三处 SQL 加 `AND COALESCE(is_deleted, FALSE) = FALSE`。

### 问题 3：OIDC 登录会复活被禁用的用户

**位置**：`repo/services/auth-service/internal/service/oidc_sessions.go` CreateSession 的 users upsert

**现象**：upsert 冲突分支 `SET status='active'`，管理员禁用的用户一次 SSO 登录即可解禁。

**解决办法**：

- upsert 不再触碰 `status` 字段（去掉 `status='active'`）
- 登录前先查已存在用户的状态，`disabled` 或软删除则拒绝登录

### 问题 4：冻结租户的错误语义需产品决策

**位置**：`repo/pkg/adapters/postgres/password_login.go` LookupTenant

**现象**：LookupTenant 只放行 `active`，冻结租户的用户登录得到 `TENANT_NOT_FOUND`（404），既误导用户，也隐含一个反向取舍：若区分 `TENANT_FROZEN` 错误码，会向未认证调用者泄露租户存在性。

**待决策**：冻结租户对存量会话的预期行为——

- 方案 A：frozen = 仅阻止新登录、存量会话自然过期 → 当前登录行为已对，只需调整错误码语义
- 方案 B：frozen = 立即断流 → 除错误码外，还必须在问题 1 的 refresh 校验中拦截冻结租户续期

**决策人**：产品/架构（代码方案随决策变化，暂不实现）。

### 问题 5：角色快照过期，且 legacy/V2 行为不一致（次要）

**位置**：

- `repo/services/auth-service/internal/service/auth_service.go` CheckPermission（legacy，按 token 内 roles 判定）
- `repo/pkg/adapters/postgres/password_login.go` LoadRoles（空角色兜底 `["user"]`）
- `repo/services/auth-service/internal/service/permissions.go` userPermissions（V2，空角色 → 权限为空 → 全 deny）

**现象**：

- `refresh_tokens.roles` 是登录时刻快照，续期签发的新 access token 继续携带旧角色。撤销 `tenant-admin` 角色后，用户仍能凭旧角色走 legacy CheckPermission 最长 7 天；V2 CheckPermissionV2 每次重读库，不受影响
- 不一致：管理员删除用户唯一角色后，LoadRoles 兜底 `["user"]` 使登录成功且 legacy 放行，但 V2 权限为空全 deny

**解决办法**：

- Refresh 续期时从 `user_roles` 重读角色，而非沿用快照
- LoadRoles 空角色时直接拒绝登录，与 V2 fail-closed 语义对齐

### 问题 6：平台角色扩展（platform-ops / platform-readonly）与登录链路不兼容

**依据**：`租户管理plan v3.0.md` §4.1.5——平台角色从仅 platform-admin 扩展为三角色；`repo/api/openapi/services/v1.yaml` 的 PlatformAdmin 系列 schema/enum 已含三角色。

**当前落地状态**（2026-09-07 核实）：

- seed migration `20260831000100_platform_roles_seed.sql` 已存在，两角色 permissions 均为规范数组格式，符合 `roles_permissions_schema` CHECK 约束
- 平台账号管理面（创建/改角色/重置密码/启停/软删/角色列表/权限查询）三层已完整实现
- 但**登录链路仍停留在单角色时代**——以下 5 个断点全部未修

**平台角色权限矩阵（seed migration 实际落地值）：**

| 角色 | tenants | resource_pool | metering | 平台账号管理（users） | 审计导出 |
|---|---|---|---|---|---|
| platform-admin | `*`（`{"resource":"*"}`） | `*` | `*` | `*` | `*` |
| platform-ops | `*` | `*` | read+list | 无条目（none） | 无条目（none） |
| platform-readonly | read+list | read+list | read+list | 无条目（none） | 无条目（none） |

> 注：plan 中 platform-readonly 的 audit_export=read 与 seed 落地值（metering read，audit 无条目）存在出入；plan 的 4 维度命名（tenant_ops / resource_pool / platform_user / audit_export）与 seed 实际 resource 命名（tenants / resource_pool / metering）也不同——plan 为产品语义，seed 为数据库语义，两套命名并存。断点 6d 实施时需以 seed 的 resource 命名为准做权限映射。

**断点 6a：平台登录只认 platform-admin，新角色用户无法登录**

- 位置：`repo/pkg/adapters/postgres/password_login.go` platformLoginStore.LookupUser
- 现象：EXISTS 子查询硬编码 `r.name='platform-admin'`，platform-ops / platform-readonly 用户登录一律返回 `INVALID_CREDENTIALS`。管理面已能创建新角色账号（Core Create 按 `role_id` 解析角色、Services 不白名单三角色），但创建出来的账号无法登录——功能闭环断裂
- 解决：改为 `r.name IN ('platform-admin', 'platform-ops', 'platform-readonly')`（或与 Store 一致用 `r.name LIKE 'platform-%'`，但显式 IN 白名单更安全，防止误建 `platform-xxx` 角色自动获得登录资格）；同时 port 注释（`repo/pkg/ports/password_login.go`）同步更新三角色集合

**断点 6b（已解决，记录保留）：roles 表新角色 seed 曾缺失 / plan 的 seed SQL 格式与数据库约束冲突**

- 已落地：migration `20260831000100_platform_roles_seed.sql` 用规范数组格式写入两角色，符合 CHECK 约束；"无权限"用省略条目表达（migration 注释明确说明不写 `"actions":[]` 的原因）
- 遗留经验：plan §4.1.5 草稿的对象格式 `{"tenant_ops":"write",...}` 与 `roles_permissions_schema` CHECK 冲突，落地时已改写为数组格式。**后续新增角色时 seed 一律用数组格式 + 省略条目表达 none**，勿照抄 plan 草稿

**断点 6c：角色兜底逻辑会放大权限**

- 位置：
  - `repo/pkg/adapters/postgres/password_login.go` platformLoginStore.LoadRoles（空角色兜底 `["platform-admin"]`）
  - `repo/services/auth-service/internal/service/token_issuer.go` IssuePlatformAccessToken（roles 为空时兜底 `platform-admin`）
- 现象：平台账号角色被解绑后（ChangeRole 的 UPDATE 失败中间态、或平台侧误删 user_roles 行），兜底会把无角色用户升级为超级管理员。注意管理面 ChangeRole 是"UPDATE user_roles SET role_id"而非先删后插，user_roles 行始终存在，兜底触发概率低但一旦触发即权限放大
- 解决：两处兜底删除；空角色直接拒绝登录（与问题 5 的 fail-closed 方案合并实施）

**断点 6d：legacy CheckPermission 不认新角色 → 全 deny**

- 位置：`repo/services/auth-service/internal/service/auth_service.go` CheckPermission
- 现象：只放行 platform-admin / tenant-admin（`hasRole` 判定），platform-ops / platform-readonly 的 token 在 legacy 路径全部 403。Services 层 `/api/v1/svc/*` 路由（plan 的 tenants / platform-admins 端点全在此前缀）由 Gateway rbac.go legacy 路径调 CheckPermission → 新角色用户即使登录成功（6a 修复后）也用不了任何端点
- 解决：CheckPermission 的平台分支按新角色扩展；或将 plan 的端点全部走 V2 generated 路径（CheckPermissionV2 权威读库，天然支持新角色——V2 按权限矩阵判定，platform-readonly 的 tenants read+list 自动放行只读端点）。plan 中"Gateway AuthZ 中间件按角色名硬编码校验"的表述与 V2 架构方向冲突，建议以 V2 权威读库为准，硬编码仅作为过渡
- 注意：V2 路径的权限判定基于 `roles.permissions` 的 resource/actions——需核对 Gateway V2 策略（`generate_gateway_authz.py` 生成的 generated_authz）中 resource 命名与 seed 的 tenants / resource_pool / metering 是否一致，不一致则新角色在 V2 路径同样全 deny

**断点 6e：JWT 内 roles 与 V2 权威权限的一致性**

- 位置：`repo/services/auth-service/internal/service/token_issuer.go` IssuePlatformAccessToken
- 现象：token 携带登录时角色名（legacy roles projection），V2 不读 token roles、每次重读 `user_roles`。管理面 ChangeRole（UPDATE role_id）后：V2 路径立即生效，legacy 路径要等 token 过期（最长 1h access + 7d refresh 续期快照）——与问题 5 同根
- 解决：随问题 5 的 refresh 重读角色方案一并解决；角色变更端点可选吊销该用户全部 refresh token（`UPDATE refresh_tokens SET revoked_at=NOW() WHERE user_id=...`）实现即时生效

### 问题 7：平台账号生命周期操作不吊销既有会话（管理面新引入）

**依据**：平台账户模块（Core `platform_user_admin.go` / Services `platform_admin_service.go` / Gateway 双路由）已完整实现，但所有写操作只改数据库行，不触碰 `refresh_tokens` / token 黑名单——与登录模块（auth-service）完全解耦。

**现象**（对照管理面各操作逐一核对登录链路）：

| 管理面操作 | 数据变更 | 登录侧即时效果 | 缺口 |
|---|---|---|---|
| `POST /platform-admins/{id}/disable`（SetStatus disabled） | `users.status='disabled'` | 新登录被拒（platform_login.go 校验 `status='active'`，✓） | **存量 refresh token 未吊销**：续期不查用户状态（问题 1），被禁用账号 7 天内可持续续期 |
| `POST .../reset-password`（ResetPassword） | `users.password_hash` 更新 | 无 | **旧会话全部存活**：密码重置预期使旧凭据失效，但旧 access + refresh token 仍有效至自然过期（最长 1h + 7d） |
| `PUT .../{id}/role`（ChangeRole） | `user_roles.role_id` UPDATE | 无 | token 内 roles 仍为旧角色——V2 路径即时生效，legacy 路径沿用旧角色（问题 6e 同根） |
| `DELETE .../platform-admins/{id}`（SoftDelete） | `is_deleted=TRUE, status='disabled'` | 无 | 同 disable：存量 refresh token 未吊销；且登录 LookupUser 不查 `is_deleted`（问题 2 平台版） |

**与租户侧对照**：租户管理面同样不吊销会话（问题 1/2 的根因相同），平台侧因账户数量少、权限大（超管/运营），风险更高。

**解决办法**（与问题 1 的 Refresh 状态校验互补，双保险）：

1. **被动防御（必做，随问题 1）**：Refresh 续期 JOIN users 校验 `status='active' AND is_deleted=FALSE`——兜住 disable / delete 两类操作
2. **主动吊销（建议）**：管理面 disable / reset-password / soft-delete 三个操作在 Core Store 事务内追加 `UPDATE refresh_tokens SET revoked_at=NOW() WHERE user_id=$1 AND revoked_at IS NULL`，实现即时断流；Services 层操作后向 auth-service token 黑名单写入该用户已签发 access token 的 jti 不可行（无法枚举），access token 只能等 1h 自然过期，属可接受窗口
3. **审计补强**：Services 审计 `platform_admin.disable` / `platform_admin.reset_password` / `platform_admin.delete` 已落 `audit_logs`，若实施主动吊销，吊销行数可写入 details 便于追溯

**涉及模块**：`repo/pkg/adapters/runtime/platform_user_admin.go`（Store 事务内追加吊销）、`repo/pkg/ports/platform_user_admin.go`（接口无签名变化，吊销在实现内部完成，可选新增端口方法供租户侧复用）

## 六、平台账户模块当前实现速查（2026-09-07 核实）

为后续实施问题 6/7 提供上下文，三层结构与关键行为：

**分层链路**：Gateway 双路由（`/api/v1/admin/platform-users*` 直连 Core Store；`/api/v1/svc/platform-admins*` 经 gRPC 调 platform-settings-service）→ Services `PlatformAdminService`（校验 + Core client + `platform_admin.*` 审计）→ Core `PostgresPlatformUserAdminStore`（`WithPlatformTx` bypass RLS，单事务）。

**Core Store 关键行为**（`repo/pkg/adapters/runtime/platform_user_admin.go`）：

- Create：username 唯一性（`tenant_id IS NULL AND is_deleted=FALSE`）→ `lookupPlatformRoleNameByID`（仅接受 `name LIKE 'platform-%'` 且 `tenant_id IS NULL` 的角色）→ 插入 users（`local:` 前缀、status=active）+ user_roles
- List/Get：JOIN 平台角色，排除软删除；search 用 `REGEXP_REPLACE` 剥前缀后 ILIKE
- ChangeRole：UPDATE `user_roles.role_id`（非先删后插）；降级最后活跃 platform-admin → `ErrLastPlatformAdmin` 拒绝
- SetStatus：禁用最后活跃 platform-admin → 拒绝；重复状态 → `ErrStatusUnchanged`
- SoftDelete：置 `is_deleted=TRUE, deleted_at, status='disabled'` 三字段；最后管理员保护
- ResetPassword：Core 侧 bcrypt 校验与旧不同（`ErrPasswordSameAsOld`），密码复杂度双校验（Services 预校验 + Core 强校验：8-64 字符、≥3 类）
- ListPlatformRoles：按 `name LIKE 'platform-%'` 返回，seed 后含三角色
- 最后管理员保护统计口径：`status='active' AND is_deleted=FALSE AND r.name='platform-admin'`，排除操作目标自身

**Services 层**（`platform_admin_service.go`）：Create/ChangeRole/ResetPassword/Disable/Enable/Delete 均写审计（成功记 target_id + 上下文，失败记错误；密码永不入审计）；List/Get/Permissions/Roles/AuditLogs 只读不审计；username 对外剥 `local:`/`oidc:` 前缀，source 由前缀推断（`third_party`/`local`/`unknown`）。

**与登录模块的耦合点（问题 6/7 的根因）**：管理面通过 `user_roles`/`users`/`roles` 三表写数据，登录模块（auth-service passwordLoginStore）读同一批表——但两侧 SQL 条件不一致（管理面查 `is_deleted=FALSE` + `platform-%`，登录白名单只 `platform-admin` 且不查 is_deleted），且管理面不吊销 `refresh_tokens`。
