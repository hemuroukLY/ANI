### 1. MFA 设计：用户级与租户级分离

#### 问题

1. **无法对单个用户强制 MFA** — 租户级开关作用于租户所有用户，粒度太粗
2. **平台运营账户无租户** — `tenant_id IS NULL`，不关联 `tenant_auth`，无法展示 / 配置 MFA
3. **职责混淆** — 租户管理员列表展示的是"租户 MFA"而非"该用户 MFA"，语义错误

#### 设计方案

**用户级 MFA（新增）**

在 `users` 表新增用户级 MFA 强制字段：

```sql
ALTER TABLE users ADD COLUMN mfa_required BOOLEAN NOT NULL DEFAULT FALSE;
```

| 字段 | 表 | 类型 | 默认值 | 级别 | 作用域 |
|------|------|------|--------|------|--------|
| `mfa_required` | `users` | BOOLEAN | FALSE | **用户级**（新增） | 单个用户 |
| `mfa_required` | `tenant_auth` | BOOLEAN | FALSE | **租户级**（已有） | 租户所有用户 |

**并集生效规则**

任一为 TRUE 即强制 MFA：

- `users.mfa_required=TRUE` → 该用户无论租户配置如何，登录必须 MFA
- `tenant_auth.mfa_required=TRUE` → 该租户所有用户登录必须 MFA
- 平台运营账户（`tenant_id IS NULL`）→ MFA 仅由 `users.mfa_required` 决定（无租户级 MFA 参与）

**展示规则**

| 页面 | MFA 列含义 | 数据来源 |
|------|-----------|----------|
| 租户列表 `/boss/tenants` | **不含 MFA** | — |
| 租户详情 `/boss/tenants/{id}` | **不含 MFA** | — |
| 租户安全页 `/boss/tenants/{id}/security` | **租户 MFA**（Switch 操作） | `tenant_auth.mfa_required` |
| 租户管理员列表 `/boss/tenants/{id}/admins` | **用户 MFA** | `users.mfa_required` |
| 跨租户管理员列表 `/boss/tenant-admins` | **用户 MFA** | `users.mfa_required` |
| 平台账号列表 `/boss/settings/platform-admins` | **用户 MFA** | `users.mfa_required` |

#### Gateway 登录链路 MFA 校验（目标设计）

```
Gateway 登录链路：JWT 校验 → 解出 tenant_id

租户账号（tenant_id 非空）：
  查 tenant_auth.mfa_required（租户级）+ users.mfa_required（用户级）
  - 任一为 TRUE 且用户未完成 MFA → 403 MFA_REQUIRED
  - 二者均为 FALSE → 遵循用户级 MFA enrollment 配置

平台账号（tenant_id 为空）：
  查 users.mfa_required（用户级）
  - TRUE 且用户未完成 MFA → 403 MFA_REQUIRED
  - FALSE → 遵循用户级 MFA enrollment 配置
```

错误码 `MFA_REQUIRED`（403）：租户级或用户级已启用 MFA 强制，但用户未完成 MFA 二次校验。

#### 注意事项

1. **pb 生成代码**：`tenant_admin_service.pb.go` 中的 struct + getter 需同步修改，raw descriptor 需重新执行 `protoc` 生成。
2. **MFA secret 存储**：`users.mfa_secret_encrypted` 字段由后续 PR 添加，不在本次设计范围。
3. **用户级 MFA enrollment 端点**：`POST /api/v1/auth/mfa/enroll` 等属 auth-service 现有职责，不在租户管理范围。
4. **MFA 校验形式**：仅 TOTP（Google Authenticator / 1Password 等），不包含 SMS / 邮箱验证码。
5. **tenant-auth 层级**：如需将 tenant-auth 端点（SSO/MFA）从 Services 层移至 Core API 层（`/api/v1/admin` 前缀），需额外修改 plan §5.0 / §5.2.8-5.2.11 / §6.3.6-6.3.8 / §8 / §7.3.7 / §9.1 / 实施计划表。

### 2. SSO 第三方连接验证：搭建 Windows Server AD 测试环境

**状态：** 待实施
**关联：** plan v3.0 §4.1.2 / §5.2.8 / §6.3.6 / §7.3.7

#### 背景

当前 OIDC 单点登录链路使用 Dex 作为 IdP，开发环境仅通过静态密码（`admin@ani.local`）验证。尚未对真实第三方目录服务（Active Directory / LDAP）做过端到端连接验证。需要在可控环境中搭建 Windows Server + AD，作为真实企业身份源，测试 Dex LDAP Connector 与 ANI OIDC 登录链路的完整集成。

#### 目标

1. 在 Windows Server 虚拟机上部署 Active Directory 域服务
2. 创建测试用户与安全组，模拟企业组织结构
3. 配置 Dex LDAP Connector 连接 AD
4. 验证 ANI Console / BOSS OIDC 登录链路：AD 用户 → Dex → auth-service → JWT 签发
5. 验证 `oidcGroupRoleMapper` 将 AD 安全组正确映射为 ANI 平台角色

#### 环境准备

| 组件 | 说明 |
|------|------|
| Windows Server 虚拟机 | 建议 Windows Server 2022 (Hyper-V / VMware / VirtualBox) |
| Active Directory 域服务 | 新建林，域 `test.ani.local`，DC `dc01.test.ani.local` |
| Dex | 现有 docker-compose 启动，新增 LDAP Connector |
| auth-service + ani-gateway | 现有开发环境部署 |

#### 实施步骤

1. **搭建 AD 域控**
   - 安装 Windows Server，配置静态 IP（如 `192.168.56.10`）
   - 添加 AD DS 角色，提升为域控：林 `test.ani.local`
   - 在 DNS 中确保 Dex 宿主机可解析 `dc01.test.ani.local`

2. **创建测试用户与安全组**
   - OU `ANI Users` 下创建测试用户
   - 安全组 `ani-admins`、`tenant-admin`、`platform-admins` 分别加入对应用户
   - 用户设置 `userPrincipalName`（如 `admin@test.ani.local`）

3. **配置 Dex LDAP Connector**
   - 修改 `dex-dev.yaml`，新增 `connectors` 段：

   ```yaml
   connectors:
     - type: ldap
       id: ad
       name: Active Directory
       config:
         host: 192.168.56.10:636
         insecureNoSSL: false
         insecureSkipVerify: true
         bindDN: CN=dex-svc,OU=Service Accounts,DC=test,DC=ani,DC=local
         bindPW: <dex-svc-password>
         usernamePrompt: AD 账号
         userSearch:
           baseDN: OU=ANI Users,DC=test,DC=ani,DC=local
           filter: "(objectClass=user)"
           username: userPrincipalName
           idAttr: DN
           emailAttr: userPrincipalName
           nameAttr: displayName
         groupSearch:
           baseDN: OU=ANI Users,DC=test,DC=ani,DC=local
           filter: "(objectClass=group)"
           userMatchers:
             - userAttr: DN
               groupAttr: member
           nameAttr: cn
   ```

   - 在 AD 中创建服务账号 `dex-svc`，授予对 `ANI Users` OU 的读取权限

4. **配置 auth-service 组角色映射**
   - 设置 `AUTH_OIDC_GROUP_ROLE_MAP_JSON`：
   ```json
   {"ani-admins":["tenant-admin"],"platform-admins":["platform-admin"],"tenant-admin":["tenant-admin"]}
   ```

5. **端到端验证**
   - 从 Console 登录页选择"企业登录"，输入 `tenant_name`
   - Dex 页面展示 AD Connector，点击后输入 AD 账号密码
   - 验证回调后 auth-service 签发 JWT，`roles` 正确映射
   - 验证 BOSS 平台登录链路（AD 用户属 `platform-admins` 组 → `platform-admin` 角色）
   - 用 `scope_allowed_for_path` 校验路由隔离（平台账号访问 `/api/v1/platform/*`，租户账号访问 `/api/v1/*`）

#### 验收标准

- [ ] AD 域控可访问，`ldapsearch` 可查询测试用户
- [ ] Dex 启动后 LDAP Connector 状态正常（`/dex/.well-known/openid-configuration` 列出 `ad` connector）
- [ ] Console OIDC 登录：AD 用户登录成功，返回有效 JWT，`roles` 含正确角色
- [ ] BOSS OIDC 登录：AD 平台管理员登录成功，`scope=platform`
- [ ] AD 安全组变更（加入/移除用户）后重新登录，角色映射随之变化
- [ ] `oidcGroupRoleMapper` 拒绝白名单外的组名（如 `custom-group` 不映射为任何角色）

#### 注意事项

1. **TLS 证书**：AD LDAPS（636）默认使用自签证书，Dex 配置 `insecureSkipVerify: true` 仅限测试环境；生产环境需导入 AD CA 到 Dex 容器信任库。
2. **网络连通性**：确保 Dex 容器可访问 AD 主机 IP，docker-compose 网络默认 `bridge`，需确认路由可达。
3. **DNS 解析**：AD Kerberos 依赖 SRV 记录，但 Dex LDAP Connector 仅需 A 记录或直连 IP。
4. **账号锁定**：测试时注意 AD 组策略默认账户锁定策略，避免反复密码错误导致 `dex-svc` 被锁。
5. **不影响现有链路**：此测试为新增 Connector，不改动现有密码登录与静态密码 DB Connector，`enablePasswordDB` 可保留。
