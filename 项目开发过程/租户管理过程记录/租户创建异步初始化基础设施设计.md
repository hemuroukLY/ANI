## 1. 背景与问题

### 1.1 两个 404 案例

**案例一：镜像仓库 404**

租户 test3（tenant_id=`cfe88569-4960-434c-ad6f-4d78e70fc80d`）访问 `GET /api/v1/registry/images?limit=100&purpose=system` 返回：

```json
{"code": "NOT_FOUND", "message": "capability resource not found"}
```

根因：Harbor 模式下 `ListImages` 无 project 参数时默认 project=tenant_id，调 `GET /api/v2.0/projects/{tenant_id}/repositories`，而该租户在 Harbor 中**没有同名项目** → Harbor 404 → `ports.ErrNotFound`。

**案例二：负载均衡器 404**

租户 test3 创建 LB（`lb-d63514dc-…`）时，KubeOVN provider 对 Service 执行 SSA PATCH：

```
PATCH /api/v1/namespaces/ani-tenant-cfe88569-…/services/lb-lb-d63514dc-…
→ 404 namespaces "ani-tenant-cfe88569-…" not found
```

根因：**网络资源（VPC/子网/LB/安全组/路由）的 KubeOVN provider apply 路径从不创建租户命名空间**，只有 platform-workload 路径会先 apply Namespace manifest。新租户未创建过工作负载时，任何网络资源创建必然 404。

### 1.2 共同根因

租户的**基础设施面资源**（Harbor 项目、K8s Namespace）当前是**惰性初始化**，且惰性路径有缺口：

| 资源 | 当前创建时机 | 方式 | 缺口 |
|------|------------|------|------|
| K8s Namespace | 首个 workload 创建时 | `renderPlatformWorkloadNamespace` 自动 apply | 网络资源路径无人创建 ✗ |
| Harbor 项目 | 首个 pull-secret / 手动 `POST /registry/projects` | `EnsureProject` 自动 | ListImages 等只读路径不创建 ✗ |

**需求**：创建租户（CreateTenant）成功后，**异步**完成：
1. Harbor 中创建与 tenant_id 同名的镜像仓库项目
2. K8s 中创建 `ani-tenant-<tenant_id>` 命名空间

### 2.1 CreateTenant 完整链路

```
BOSS 前端
  → POST /api/v1/svc/tenants                     （gateway tenant_list_resources.go:38）
  → tenant-service gRPC TenantService.CreateTenant （tenant_service.go:264-372）
      步骤 1-5：入参校验 / 套餐校验 / 配额视图 / bcrypt
```

**关键事实**：
- 落库的唯一入口是 gateway 的 Core handler（`admin_tenant_resources.go:88`），tenant-service 只是编排层
- **Harbor 客户端（HarborImageRegistry）与 K8s 客户端（KubernetesRESTClient）都在 gateway 进程内组装**（`registry_runtime.go:77`、`router.go:22/28` 注入 RegisterOptions）；tenant-service 没有任何基础设施凭证（刻意的职责边界）
- 已有**异步补偿先例**：`scheduleQuotaSyncRetry`（[tenant_plan_service.go:923](file:///d:/Jczn/project/ANI/ANI/repo/services/tenant-service/internal/service/tenant_plan_service.go#L923)）：goroutine + 退避重试 + 每次失败写审计 + 单测开关 `enablePutQuotaRetry`

### 2.2 可复用的幂等原语

| 原语 | 位置 | 幂等性 |
|------|------|--------|
| `ImageRegistry.EnsureProject(ctx, tenantID)` | [harbor_image_registry.go:112](file:///d:/Jczn/project/ANI/ANI/repo/pkg/adapters/registry/harbor_image_registry.go#L112) | List 后无则 Create；并发创建冲突（isConflict）视为成功 |
| `renderPlatformWorkloadNamespace(tenantID)` | [kubernetes_platform_workload_runtime.go:388](file:///d:/Jczn/project/ANI/ANI/repo/pkg/adapters/runtime/kubernetes_platform_workload_runtime.go#L388) | 纯渲染，产 Namespace manifest（labels：`app.kubernetes.io/part-of= ani-platform` + 租户标签） |
| `KubernetesRESTClient.ApplyManifests` | SSA（server-side apply） | 同一 manifest 重复 apply 无副作用；`compensateAppliedManifests` 回滚时跳过 Namespace，天然安全 |

### 2.3 权威约束（来自既有实现）

- Harbor 项目名**必须等于 tenant_id**（`harbor_image_registry.go:89` 校验 `project must match tenant id`）
- K8s Namespace 名为 `ani-tenant-<tenant_id>`（`tenantNamespace()`），标签必须与 workload 路径**完全一致**（避免标签漂移导致 SSA 字段管理冲突）——因此必须复用 `renderPlatformWorkloadNamespace`，不得另写一份渲染
- Core `/admin/*` 端点已有平台凭证鉴权（CORE_API_TOKEN / auth-service minter 双层凭证，tenant-service `main.go:23` 已配置）

## 3. 方案选型

### 候选方案

**方案 A：gateway Core handler 落库成功后进程内异步 provision**
在 `admin_tenant_resources.go` 的 createTenant handler 落库成功后起 goroutine，直接调 `EnsureProject` + namespace apply。

**方案 B（推荐）：tenant-service 编排 + gateway 新增幂等 provision 端点**
tenant-service `CreateTenant` 步骤 7 之后新增异步编排（复刻 `scheduleQuotaSyncRetry` 模式），经 Core SDK 调用 gateway 新端点 `POST /admin/tenants/{id}/provision`。

**方案 C（否决）：tenant-service 内嵌 K8s/Harbor 客户端**
违反现有分层：tenant-service 是无状态编排层，不持有基础设施凭证；需要给它发 ServiceAccount/Harbor 密码，攻击面和部署复杂度陡增。

### 对比

| 维度 | A（gateway 内嵌） | B（编排+端点，推荐） | C（内嵌客户端） |
|------|-----------------|-------------------|---------------|
| 与 quota init 模式对称性 | ✗ 编排点分裂 | ✓ 完全同构（审计/重试/开关复刻一套） | ✗ |
| 审计归属 | ✗ gateway 无 AuditStore 注入，失败审计要新开通路 | ✓ tenant-service 持有 AuditStore，writeAuditFailure 直接可用 | ✗ |
| 覆盖直调 Core 的创建路径 | ✓ | ✗（仅 tenant-service 编排路径触发；直调属内部运维操作，可接受） | ✓ |
| 存量租户补建复用 | 需另想办法 | ✓ 端点天然可被运维脚本复用 | ✗ |
| 新增跨服务调用 | 无 | +1 跳（同现有 SDK 调用路径，无新依赖） | 无 |
| 改动面 | 小 | 中（3 处：端点/SDK/编排） | 大 |

**决策：方案 B。** 核心理由：与已验证的 `scheduleQuotaSyncRetry` 模式**完全同构**（同位置、同退避、同审计、同单测开关范式），且 provision 端点可复用为存量租户补建工具。直调 Core 路径不触发 provision 属可接受边界（Core admin API 面向内部服务，人工直调后可手动跑一次 provision）。

## 4. 总体设计

### 4.1 时序

```
BOSS                gateway(/svc)         tenant-service              gateway(Core /admin)         Harbor/K8s
 │ POST /svc/tenants     │                      │                            │                        │
 │──────────────────────>│                      │                            │                        │
 │                      │──gRPC CreateTenant───>│                            │                        │
 │                      │                      │──POST /admin/tenants──────>│                        │
 │                      │                      │                            │──5表事务落库──>        │
 │                      │                      │<─────── Tenant ────────────│                        │
 │                      │                      │──quota init(步骤7)────────>│                        │
 │                      │<─200 {id,message}────│                            │                        │
 │                      │                      │ ══ gRPC 已返回，以下异步 ══                        │
 │                      │                      │──POST /admin/tenants/{id}/provision──>│             │
 │                      │                      │                            │──EnsureProject────────>│ Harbor
 │                      │                      │                            │──ApplyManifests(NS)──>│ K8s
 │                      │                      │<─────200 {ensured…}────────│                        │
 │                      │                      │──审计 tenant.infra_provisioned─>DB                  │
```

**最终一致窗口**：CreateTenant 响应**不等待** provision 完成（秒级）。前端创建租户后通常跳转列表页，窗口可接受；调用方需要强一致时可显式调 provision 端点或轮询。

### 4.2 端点契约

```
POST /api/v1/admin/tenants/{tenant_id}/provision
Authorization: Bearer <平台凭证>   （现有 Core admin 鉴权中间件覆盖，无新权限模型）
```

请求体：无（tenant_id 路径参数）。

响应 200：

```json
{
  "tenant_id": "cfe88569-4960-434c-ad6f-4d78e70fc80d",
  "registry_project": {"ensured": true},
  "namespace": {"ensured": true}
}
```

语义：**确保存在**（ensured），不区分"新建 vs 已存在"（`EnsureProject` 与 SSA 均不返回该信息，且对调用方无意义）。

错误映射（复用 `writeAdminTenantError` 风格）：

| 场景 | HTTP | code |
|------|------|------|
| tenant_id 非法 | 400 | VALIDATION_FAILED |
| 租户不存在（provision 前必须 `GetTenant` 校验，防幽灵 ID 乱建项目） | 404 | TENANT_NOT_FOUND |
| Harbor/K8s 真实失败（5xx、超时） | 500 | INFRA_PROVISION_FAILED |
| K8s 客户端未配置（本地/docker 环境） | 200 降级 | —（见 §7 降级） |

**幂等性**：端点天然幂等（EnsureProject + SSA），重复调用返回 200。不挂 Idempotency-Key 中间件（那是防"同请求体重复提交"的网关层语义，本端点业务层自幂等）。

**租户状态语义**：`frozen`/`disabled` 租户允许 provision（基础设施存在不违反 freeze 语义——freeze 挡的是用户登录与资源操作，不是清理；重试窗口内租户被 freeze 的场景需要能完成）。幂等键与租户状态无关。

### 5.2 runtime 包：EnsureTenantNamespace 导出函数

**新文件：`pkg/adapters/runtime/kubernetes_tenant_namespace.go`**（与 `renderPlatformWorkloadNamespace` 同包，直接复用）

```go
// TenantNamespaceApplier 收窄 K8s apply 依赖，便于 handler 层单测注入 fake。
// KubernetesRESTClient 天然满足该接口。
type TenantNamespaceApplier interface {
    ApplyManifests(ctx context.Context, manifests []ports.WorkloadManifest) (…, error)
}

// EnsureTenantNamespace 确保租户命名空间 ani-tenant-<tenantID> 存在。
// 复用 renderPlatformWorkloadNamespace 渲染（标签与 workload 路径完全一致，
// 避免 SSA 字段管理冲突）；SSA 幂等，已存在时无副作用。
// 单独 apply 一个 manifest：compensateAppliedManifests 回滚路径会跳过 Namespace，
// 不会因后续失败删除命名空间。
func EnsureTenantNamespace(ctx context.Context, applier TenantNamespaceApplier, tenantID string) error
```

实现 3 步：tenantID 非空校验 → `renderPlatformWorkloadNamespace(tenantID)` → `applier.ApplyManifests(ctx, []ports.WorkloadManifest{ns})`。

**为什么单独成函数而不放进 KubeOVN provider**：本需求的调用方是 Core handler（非网络域），放 runtime 包避免 router 反向依赖 network_service 内部；同时该函数未来可被 `applyNetworkProvider` 修复（§8 关联问题）复用。

### 5.4 tenant-service：异步编排（复刻 quota retry 模式）

**新文件：`internal/service/tenant_infra_provision.go`**

goroutine 内部结构与 `scheduleQuotaSyncRetry`（tenant_plan_service.go:942-960）逐行同构：入参已为值拷贝（uuid 不可变）、`context.WithTimeout(Background, 10s)`、成功即 return。

**CreateTenant 接入点（[tenant_service.go](file:///d:/Jczn/project/ANI/ANI/repo/services/tenant-service/internal/service/tenant_service.go) 步骤 7 与 8 之间）：**

### 5.5 审计事件

| 事件 | action | level | details |
|------|--------|-------|---------|
| 初始化成功 | `tenant.infra_provisioned` | success/info | tenant_id、registry_project_ensured、namespace_ensured |
| 单次失败（将重试） | `tenant.infra_provision_failed` | failure/warn | tenant_id、attempt（1-3）、error |
| 3 次全败（终态） | `tenant.infra_provision_failed` | failure/error | tenant_id、attempts_exhausted: true、last_error |

审计沿用 `writeAuditSuccess` / `writeAuditFailure`（service 包已有）；resource 为 `tenant`（`auditResourceTenant`）。

## 6. 幂等与并发

| 场景 | 保障机制 |
|------|---------|
| provision 端点重复调用 | EnsureProject（List 后无则建，并发冲突容忍 `isConflict`）+ SSA（同 manifest 重放无 diff） |
| provision goroutine 与用户同时手动建 Harbor 项目 | `EnsureProject` 的 isConflict 分支吸收 |
| provision 与 workload 创建并发 apply 同一 Namespace | 两者渲染**同一函数**、同一 FieldManager（`KUBERNETES_PROVIDER_MANAGER`/`REGISTRY_PULL_SECRET_FIELD_MANAGER` 同源 env）→ SSA 合并无冲突；若 FieldManager 不同，SSA 按字段所有权共存，标签集一致故无冲突 |
| 租户创建重试（幂等键重放导致 CreateTenant 二次执行） | 事务内冲突会返回 409，provision 不会重复调度；即使重放成功路径，二次 provision 幂等 |
| 进程重启丢任务 | **不保障**（内存 goroutine，与 quota retry 同一权衡）。缓解：a) workload/pull-secret 惰性路径仍兜底可用；b) §9 存量补建脚本可随时重跑 |

## 7. 失败处理与降级

### 7.1 降级矩阵

| 环境/依赖状态 | 行为 |
|-------------|------|
| `REGISTRY_PROVIDER_MODE=local`（开发/无 Harbor） | `EnsureProject` 为 LocalImageRegistry 实现（no-op 语义），响应 `registry_project.ensured=true`，不报错 |
| gateway 无 K8s 凭证（本地 docker-compose 起 gateway） | namespace 步骤跳过：响应 `namespace.ensured=false` + reason，**不进入重试**（基础设施不存在是配置态而非故障态，重试无意义），审计记 `tenant.infra_provisioned`（details 注明 namespace_skipped） |
| Harbor/K8s 真实故障（5xx/超时/网络） | 进入 3 次退避重试；全败落终态审计。租户创建本身**不受影响**（provision 在 gRPC 返回后异步） |

### 7.2 重试参数（对齐 quota retry）

| 参数 | 值 |
|------|----|
| 最大尝试 | 3 |
| 退避 | 1s → 2s → 4s |
| 单次超时 | 10s |
| 单测开关 | `enableTenantInfraProvision = false` 禁 goroutine |

## 8. 关联问题与边界（不在本次范围，须记录）

1. **网络资源路径的 Namespace 缺口未根治**：本设计通过"预建 namespace"**缓解**了新租户创建 LB/VPC 404 的问题，但 `applyNetworkProvider`（network_service.go:1647 一带）本身仍不 ensure namespace。建议后续单独修复：render 后把 `EnsureTenantNamespace`（本设计 §5.2 导出函数）插入 apply 前——两处改动互不依赖，可并行实施。已记入[待办.md](./待办.md)的建议条目。
2. **ListImages 对无项目租户返回 404** 语义模糊（案例一）：预建项目后新租户不再触发；存量租户仍有该表现，建议产品侧决策改为空列表 200。
3. **disable/delete 租户的基础设施清理**（namespace 归属删除、Harbor 项目删除）完全不在本设计范围——当前平台无此清理机制（与登录模块记录 §7 生命周期不吊销会话同类问题）。
4. **直调 Core `POST /admin/tenants` 的创建**不触发 provision（方案 B 边界）：内部运维直调后需手动跑一次 provision 端点（幂等）。

## 9. 存量租户补建（运维步骤，复用 provision 端点）

针对已存在但缺基础设施的租户（如 test3 此前仅建了 Harbor 项目、缺 namespace）：

```bash
# 1. 平台登录拿 token（root）
TOK=$(curl -s -X POST http://<gateway>/api/v1/auth/platform/login \
  -d '{"username":"root","password":"***"}' | jq -r .access_token)
```

| 2026-09-22 | 异步而非同步 provision | 保持 CreateTenant 强一致事务语义不被基础设施故障破坏（与配额初始化同一权衡） |
| 2026-09-22 | 方案 B（编排+端点）而非 A（gateway 内嵌） | 与 quota retry 模式同构；审计/单测开关/重试全套复刻；端点可复用为存量补建工具 |
| 2026-09-22 | 复用 renderPlatformWorkloadNamespace 而非新写渲染 | 标签必须与 workload 路径一致，避免 SSA 字段管理冲突 |
| 2026-09-22 | frozen/disabled 租户允许 provision | freeze 语义挡操作不挡初始化；重试窗口内状态变化不应丢任务 |
| 2026-09-22 | K8s 未配置时降级跳过而非失败重试 | 配置态非故障态，重试无意义；本地开发环境必须可用 |
